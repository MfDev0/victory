VIctory Try 6.22 "from ScarlettPort" (what makes ScarlettPort, a VIctory-based port getting 7-22 fps on cards like yours, smoother, brought onto our engine)
- Why ScarlettPort is smoother: we went through its changes one by one. Most of its speed comes from a few defaults: no frame waits for a shader that is still compiling, small game buffers live in the card's memory instead of being read across the bus, the upscaler's 24 MB network stays on the card, and the save code never waits at boot. Each of these is now in our engine, on our own code, with a switch to turn it back
- Smoother frames: on a first run new shaders appear every frame, and each frame stood up to 250 ms waiting for them (500 before 6.15). Now nothing waits: an object whose shader is still compiling is drawn with a same-shape stand-in, or comes in a frame or two later. Compute work still waits for its shader, since a skipped compute pass can leave a scene wrong for minutes (VICTORY_PIPELINE_WAIT_MS=250 goes back)
- Speed on the card: every game buffer of 64 KB and more gets a copy in the card's memory (VICTORY_CARD_BUFFERS_MIN_KB=64; it was 2 MB). Small buffers are nearly all there are, but few bytes, and every shader read of them crossed the bus: fxceless measured the game's card time at 68.0 -> 49.8 ms a frame on an RTX 3060 12 GB. They stay inside the card buffers' cap. Not with the hybrid (H). VICTORY_CARD_BUFFERS_MIN_KB=0 goes back
- Speed on the card: 256 MB of extra room for copies of 16 MB and more, so the upscaler's network stays on the card once small copies have filled the cap (ScarlettPort: 0.1 ms instead of 56-71 ms a frame; VICTORY_CARD_BIG_ROOM=0 goes back)
- Speed on the processor: the write tracking finds its ranges by binary search and merges them in place, and does not plan twice per submission; memory windows are looked up under a shared lock (ScarlettPort measured 107 ms of lock waits per recording); no SetDescriptorHeaps or root-signature reset when the game switches between heaps that are the same heaps on the PC (VICTORY_SAME_HOST_HEAPS=0 goes back); dispatches that fit the plain path take it (fxceless #1352: card 108 -> 91 ms on a 3060; VICTORY_SPREAD_LEAN=0 goes back)
- Shaders: two exact clean-ups are on by default, also with O off (they are not the ones that lost walls in 4.5): guarded writes share one check (VICTORY_GUARD_SINK=0) and loads read four values at once (VICTORY_LOADS_WIDE=0). The shader cache rebuilds once for them

- Saves: a leftover save folder that Windows or a scanner holds is tried once and left alone, not retried under the saves' lock (that held ScarlettPort's boot for about 243 s), and a save never fails because of one
- AMD: mesh pipelines are made one at a time on AMD cards (RX 6000 players lost the card in the intro while three were made at once; VICTORY_MESH_MAKE_ONE=0 off, =1 on every card), and a save of the pipeline library no longer replaces the file the engine has mapped: the new one takes its place at the next start (VICTORY_LIBRARY_REPLACE_MAPPED=1 goes back). A shader size query is no longer reused across blocks (AMD's compiler crashed on 29 compute pipelines; Belobug #324)
- Log: every refused pipeline says why, once; a host refusal of a root signature says why; at startup a D3D12 runtime that cannot take the engine's heaps (Windows 10's built-in one) is named once, instead of thousands of refusals; out of memory says so, with Windows' and the engine's memory and what to do, instead of a bare 0xC0000409; the crash report's stack walk checks memory before reading it (VICTORY_UNWIND_CHECKS=0 goes back); the card memory line splits buffer copies (against their cap) from windows (their own cap). VIctory Try 6.17 "no wasted processor" (two causes on the processor side found in the 6.15 report)
- Speed: the game waits for its fences with two console instructions (monitorx, then mwaitx) that a PC cannot run, so each one takes an exception into Windows and back. Since 6.8 VIctory rewrites them in the game's code the first time, so they take no exception again. That worked for mwaitx, but the hot monitorx sits across two 8-byte words, where the rewrite did not fit: in the 6.15 report it failed 66 million times (patched 1, unpatched 65,974,989) and took an exception 440,000 times a second, more than a whole processor of the laptop's power budget. It is now made a 3-byte NOP that fits (it keeps its first byte and changes the other two in one store). A place that cannot be patched is no longer tried again at every exception, and the first reason is written in the log
- Speed: the pass over the game's descriptor heap (the 25,000-30,000 records the game copies into its view heap itself every frame: 22-39 ms) runs on a thread of its own beside the preparing of the submission, instead of before it on the thread the card waits for (the card stood idle 68-112 ms a frame behind it). Off again by itself if the card is lost; config.json beside=off
- Smoother frames: the pass that readies the game's buffer views for its shaders looked again at all 150,000 of them every 16th time, which made those frames take 100-180 ms of it instead of about 40. It now looks at a sixteenth of them every time, the same looks spread evenly (Kelvaroq 0055's idea; VICTORY_HEAP_AUDIT_SPREAD=0 goes back)
- The fork's copy: VIctory Try also looks for the fork at MfDev0/CATez (a repository of its own outside the GitHub fork network) when MfDev0/victory cannot be reached

VIctory Try 6.16 "room for windows" (the 3 fps cause in the 6.15 report, the flickering faces, and the disk)

VIctory Try 6.14 "one frame ahead" (the cause of 3-4 fps found and fixed; ideas from Kelvaroq and the Xbox Series S)
- Why it was 3-4 fps (6.12 report, RTX 4060, MAX on, 220 ms a frame): 130 ms of every frame the copy-back thread waited for the card to fetch what its shaders wrote, because that fetch stood in the same queue behind every frame the card still had to draw. The fast way (the card's separate copy engine) had been turned off for good on this PC by a lost card long ago, together with barrier trimming, so the card also drew with every full stop between passes. And the game heard a frame was done only after the whole copy-back. MAX lifts limits, but none of these was a limit, so it changed nothing; the 6.13 Resizable BAR fix moves memory windows, and this PC had 0 MB of them, so it could not help here either
- Speed: what the card's shaders wrote is fetched on the card's copy engine again, beside the drawing, not behind it (expected: the 130 ms wait a frame falls to a few ms). Barrier trimming is on again: the card no longer stops all work for barriers that guard nothing. Each now has its own switch, and they are the last things a lost card turns off
- Speed: one frame ahead, as on the console. On a Series S the game records the next frame while the GPU draws this one, and its present returns at once. Now a thread of VIctory's own prepares and sends the game's work, and the present goes in line behind it (VICTORY_ASYNC_SUBMIT=1, VICTORY_ASYNC_PRESENT=1, Kelvaroq's defaults: worst frames 568 -> 262 ms there). The game is never more than one frame ahead
- Speed: lazy copy-back is on again for one more try: the game hears that a frame is done before the results are copied back, and waits only if it actually reads them (it had gone off after an old crash; a new crash on a memory access turns it off again by itself)
- Speed: the card checks which parts of the game's memory changed with 64 threads per 64 KB piece instead of one thread walking 4,096 steps (VICTORY_CARD_HASH_WIDE=1; fork #1014 by martindevbr, Kelvaroq 0041: heavy frames 198 -> 120 ms with it on an RTX 5080). Neighbouring pieces are fetched in one copy (Kelvaroq 0032)
- The start screen names each of these as ON or off. If the card is lost, they go off one at a time on the next runs: wide hashes first, then one frame ahead, then the rest, with copy-engine fetches last
