VIctory Try 6.14 "one frame ahead" (why the frame rate stayed at 3-4 fps, found in the 6.12 report, and the fixes, after Kelvaroq by stellarr-studio and the Xbox Series S way of running a frame)
- Why it was 3-4 fps (6.12 report, RTX 4060, MAX on, 220 ms a frame): 130 ms of every frame the copy-back thread waited for the card to fetch what its shaders wrote, because that fetch stood in the same queue behind every frame the card still had to draw. The fast way (the card's separate copy engine) had been turned off for good on this PC by a lost card long ago, together with barrier trimming, so the card also drew with every full stop between passes. And the game heard a frame was done only after the whole copy-back. MAX lifts limits, but none of these was a limit, so it changed nothing; the 6.13 Resizable BAR fix moves memory windows, and this PC had 0 MB of them, so it could not help here either
- Speed: what the card's shaders wrote is fetched on the card's copy engine again, beside the drawing, not behind it (expected: the 130 ms wait a frame falls to a few ms). Barrier trimming is on again: the card no longer stops all work for barriers that guard nothing. Each now has its own switch, and they are the last things a lost card turns off
- Speed: one frame ahead, as on the console. On a Series S the game records the next frame while the GPU draws this one, and its present returns at once. Now a thread of VIctory's own prepares and sends the game's work, and the present goes in line behind it (VICTORY_ASYNC_SUBMIT=1, VICTORY_ASYNC_PRESENT=1, Kelvaroq's defaults: worst frames 568 -> 262 ms there). The game is never more than one frame ahead
- Speed: lazy copy-back is on again for one more try: the game hears that a frame is done before the results are copied back, and waits only if it actually reads them (it had gone off after an old crash; a new crash on a memory access turns it off again by itself)
- Speed: the card checks which parts of the game's memory changed with 64 threads per 64 KB piece instead of one thread walking 4,096 steps (VICTORY_CARD_HASH_WIDE=1; fork #1014 by martindevbr, Kelvaroq 0041: heavy frames 198 -> 120 ms with it on an RTX 5080). Neighbouring pieces are fetched in one copy (Kelvaroq 0032)
- The start screen names each of these as ON or off. If the card is lost, they go off one at a time on the next runs: wide hashes first, then one frame ahead, then the rest, with copy-engine fetches last

VIctory Try 6.13 "NVIDIA fixes" (from a deep search of the NVIDIA forks: trustno1-coder/VIctory-NVIDIA and edsuuu/VI-BR-PORT, ported into this fork's engine)
- Memory: on PCs with less than 24 GB of memory, the game's memory windows go straight into the card's memory through Resizable BAR: one copy, none in the PC's memory, nothing to send each frame (Indy2l at trustno1-coder/VIctory-NVIDIA: on a 16 GB RTX 3060 PC the out-of-memory error 0x8007000E and the driver crash a minute in went away, shared memory stayed at 4.4 GB instead of 7.5, 1.6-3 -> 10-12 fps). Up to 20% of a card under 8 GB (about 1.2 GB of a 6 GB card), 30% above, 35% with MAX. Nothing changes if Resizable BAR is off in the BIOS. If the card is lost with it on, it goes off by itself for the next run. VICTORY_WINDOWS_BAR_MB sets it by hand
- Speed: texture read-backs (the water maps the game reads back) are written into the game's memory by a thread of their own. Before, every finished frame waited for them, 100-400 ms in frames where the world streamed (VICTORY_TEXBACK_ASYNC=0 goes back)
- Shader stutter: a pipeline that is still compiling is waited for in one frame only; the frames after it go on (the object appears once it is ready) instead of freezing half a second a frame. Compute shaders start compiling as soon as the game creates them
- Picture: the face and skin decoration bake is found by name (51 programs, not 4 hashes): cutscene faces no longer come out black or flat
- Picture: streamed textures are no longer forgotten when the game changes a lot of memory at once (the list of changed memory is merged when full, never emptied)
- Stability: the card's buffer compare goes to the card on its own submission (D3D12 error 538 on NVIDIA)

VIctory Try 6.12 "all-out" (no caps mode; ray-only passes left out; fixes from edsuuu/VI-BR-PORT and trustno1-coder/VIctory-NVIDIA ported into this fork's engine)
- MAX (type MAX, then Enter): all-out mode. VIctory Try reads this PC (CPU threads, memory, card memory) and lifts VIctory's own caps to all of it but about 1%: every CPU thread but one for copy-back, texture detiling and pipeline compiles; the process at high priority (never realtime) with a soft hold on 90% of the memory; textures up to 99% of the card (90 before), no texture cap (the low preset's 1536 MB), 512 MB of texture uploads a frame (192), more of the game's buffers compared on the card, 256 MB DirectStorage reads in flight; the memory guard holds uploads back only at about 1% free (1 GB before) and the card at 98-99% full (85-97). If the card is lost, all-out goes off by itself for the next run. VICTORY_TRY_ALL_OUT=1 turns it on too
- Speed: with ray tracing skipped (B), the game's passes that only serve rays are not compiled and not run: the 30 bvh_skinning programs that pose every character a second time just for the ray structures (the largest share of the card's time in a cutscene: 6.8 -> 10.2 fps on an RTX 4060 Ti 8 GB at edsuuu/VI-BR-PORT), about 1,000 CS_RaytracingResolve programs, the probe ray picking, and the traces against structures that are never built (the Voxels and Fallback forms still run and light the picture). Also about 1,000 fewer pipelines to compile before and during play
- Picture: those ray-resolve passes, and 34 traced-shadow ones, turned every missed ray into light: rooms and reflections went white and hazy with the view angle (trustno1-coder/VIctory-NVIDIA's list, left out with B)
- Picture: a colour a shader writes that is NaN or infinite becomes 0 (VICTORY_NAN_SCRUB, trustno1-coder/VIctory-NVIDIA): one bad value no longer spreads through the blur and the upscaler into black blobs on faces and blocky shine where light reflects
- Every pipeline compile setting can be told: VICTORY_PIPELINE_WORKERS, VICTORY_PIPELINE_HEAVY; the memory guard's limits: VICTORY_PRESSURE_RAM_MB, VICTORY_PRESSURE_COMMIT_MB, VICTORY_PRESSURE_CARD_PERCENT (each "mild,critical"); VICTORY_PRIORITY=high; VICTORY_WORKING_SET_PERCENT

VIctory Try 6.11 "no disk stutter" (fixes from lepotane, AvatarManz and the others ported into this fork's engine)
- Shader stutter: the compiled pipelines (the 773 MB pipeline library) are read into memory before play on 16 GB PCs too. In the 6.7 report this was skipped ("too little memory free": it wanted 4 GB spare on top), so every pipeline the game needed in play was read from the disk page by page (seconds each). Now 1 GB spare is enough, and with less the front of the file is read
- Once per build, with the game closed, every shader in the game's files is translated into the cache (as AvatarManz's "victory shaders" does): a pipeline met for the first time in play then only needs the driver's compile. The first time takes 10-30 minutes; stopping it is fine. VICTORY_TRY_ALL_SHADERS=0 skips it
- Speed: parts of the game's submissions that follow one another go to the card as one (VICTORY_JOIN_PARTS, in the Y set; off by itself if the card is lost), and the copy-back work is cut into 256 KB pieces instead of 1 MB so all 12 threads share it (lepotane/VIctory-leonida)
- Picture: anisotropic samplers with point mips stay so on cards that have it (AvatarManz 011735ff; the RTX 4050 does), instead of blending between texture sizes the console does not
- The "check" test of the repository passes again (Rust sources may be up to 1 MB)

VIctory Try 6.10 "own engine + AMD upscaler" (this fork's engine is the base again; the best fixes of the others come into it)
- This fork's engine is the default again, for good. AvatarManz's and the 8 GB engine stay on N only for comparing
- The game's upscale (Series S renders 1280x720 and scales to 1080p) is now made by AMD's real PC FidelityFX upscaler, as on Belobug's engine (PortWatch #1, from DexNom): FSR 3.1 on NVIDIA cards, FSR 4 on new Radeons. Lit and reflecting surfaces should no longer turn into blocks, hair and edges stay sharp. VIctory Try downloads AMD's signed file once (57 MB from AMD's GitHub) and checks its signature every run
- T switches the upscaler: FSR (default) / own / off. If AMD's upscaler cannot run a frame, VIctory's own makes it (never a black screen)
- VIctory's own upscaler (T = own) is sharper and no longer draws the low-resolution grid into bright surfaces
- Shaders AMD's compiler made, and the game's debug shaders stored unpacked, are read now (from AvatarManz)
- The log says which upscaler ran, which AMD versions your card was offered, and how many frames carried the camera jitter the upscaler needs
